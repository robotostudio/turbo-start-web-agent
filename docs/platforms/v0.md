# Connecting a client repo to v0

For whoever at the agency is setting up a client's project on v0
(v0.app, Vercel's builder) — a one-time procedure per project.

On capability, v0 is the strongest of the supported platforms: it reads the
repository's own rulebook, shows the client the rendered site while they
work, creates its own branch off a protected base, and opens the pull
request itself. It is the only one of the four with all of those.

It also produced the single most instructive failure of the whole platform
evaluation, which §4 covers, because it is the kind no automated check will
ever catch.

## 0. Before you start

Nothing to generate. v0 reads `AGENTS.md` and `.agents/skills/` directly, so
there is no bridge file and no `harness-gen` adapter — `"v0"` does not appear
in `harness.config.json`'s `platforms` array, and adding it would fail
generation.

**This contradicts v0's own documentation, which is silent on repo
instruction files.** Verified by direct test on 2026-08-20: asked what its
rules were, a v0 chat answered *"The repo's main change rules come from the
root `AGENTS.md`, which is loaded as repository-specific instructions"* and
separately cited `.agents/skills/`, naming `compose-page` and `sync-changes`.
Re-check this if v0's behaviour appears to change; it is observed, not
contractual.

## 1. Import, and pick the repo root

v0.app → **+** in the prompt bar → **Import from GitHub**. Requires the
Vercel GitHub App with access to the repository.

Two settings matter:

- **Base branch.** Set it to the live branch (`main` here). v0 creates its
  own working branch off this and leaves the base alone, so a protected base
  branch and v0's model agree with each other by design.
- **Working directory.** v0 supports monorepos by letting you scope the
  import to a subdirectory. **Do not scope it to the app directory.**
  `AGENTS.md` and `.agents/skills/` live at the repo *root*; scoping to
  `artifacts/web` puts the entire rulebook outside what v0 can see, and it
  will behave like a platform with no instructions at all — quietly, with no
  error.

If the repo is already connected to a Vercel project, v0 offers to attach to
it. Attaching is fine: v0 works on its own branch, and branch deployments are
previews. Production only ever builds from the protected base branch.

## 2. Two things v0 does that the others don't

**It shows the client the site.** The chat has a live preview pane. For a
non-technical client this is the difference between reviewing their own copy
change and being shown a diff they cannot read — see the platform-choice
table in [`README.md`](./README.md).

**It verifies its own work in a browser.** Observed on a real content change:
it ran `pnpm content:check`, rendered the page, screenshotted it, *and*
checked that the URL it had just written actually resolved. None of that was
asked for. `AGENTS.md` rule 4 asks agents to check the rendered page; v0 is
the platform that does it without prompting.

## 3. Branch, commit, and PR behaviour

- The working branch is named from the **chat title** (e.g.
  `repository-contribution-guidelines`), not the `v0/*` pattern v0's branch
  documentation describes. Do not expect a predictable prefix.
- v0 commits under **its own git identity** (`v0 <it+v0agent@vercel.com>`),
  not the connecting user's. Better provenance than the platforms that commit
  as you.
- It **pushes the branch without being asked** and then offers a **Create PR**
  control — which matches this repo's rule 7 exactly: the commit is
  authorised by the request, the PR is the step that pauses for a human.
- It honours the commit-trailer convention from `sync-changes`, including
  swapping in `Agent: v0` unprompted.

## 4. The failure to watch for: the PR that describes the wrong thing

This is the one worth reading twice.

On a request to change one line of banner copy, v0 also ran the dev server —
correctly, to verify the change — which rewrote `next-env.d.ts`, a
Next.js-generated file. It then committed that side effect **as its own
commit with a `refactor:` prefix and a plausible rationale**, and titled the
pull request after it:

> **Improve Next.js type safety for development**
> - Updated Next.js type imports to use the development version for more
>   accurate type checking.

The banner change — the only thing anyone had asked for — was not mentioned
anywhere in the PR.

Every automated check passed, because none of them read English. A reviewer
skimming that title sees a TypeScript tweak and merges without learning that
the site's copy changed. **This is a review-gate failure, and no schema, lint
rule, or CI job can catch it.**

Two defences, and you want both:

1. **Read the diff, not the description.** On any agent-authored PR, the
   file list is the truth and the prose is a claim. This applies to every
   platform; v0 is simply where it was caught.
2. **Keep generated files out of git.** The root cause was that
   `next-env.d.ts` was tracked at all. It is gitignored now, so the dev
   server can no longer dirty the tree. Any *other* generated file that
   creeps into version control will reproduce this exactly.

Asked to fix it, v0 did well: it chose to **drop** the offending commit
rather than revert it on top, and preserved the commit trailers through the
rewrite.

### The Create PR control writes its own description, and CI puts it back

A second, separate way the description goes wrong — and this one is not the
agent's doing. v0's **Create PR** button generates its own title and body and
discards whatever the agent wrote.

On PR #28 a four-word change to `footer.yml` was titled *"Update UI
components and layout design"*. On PR #30 a change to one line of overscroll
copy got *"Sync UI enhancements and component updates from v0"* — with the
same three bullets about responsiveness and design system consistency. The
bullets are identical across two unrelated changes, so they are boilerplate
rather than a summary of anything.

Both agents' commit messages were correct, with the right trailers. The
description that would have been accurate already existed on the branch.

Three things do **not** fix this:

- **`.github/PULL_REQUEST_TEMPLATE.md`.** Verified on PR #30, opened after
  the template was on `main`. The control does not read it.
- **Git hooks.** The body is composed on v0's servers after the push. No hook
  runs at that moment, hooks are not versioned with a clone, and the
  container has no GitHub credentials to open a PR itself.
- **Asking whoever pressed the button to rewrite it.** That is the client.

So `.github/workflows/pr-describe.yml` repairs it after the fact: on a body
carrying a vendor session link — the signature of a machine-written body — it
rewrites the title from the first commit's subject and the body from the
commit messages, the changed-file list, and the trailers. The *first* commit
because v0 auto-commits every message to the chat's working branch: anything
tried mid-chat lands on the same branch as the work, on top of it. The commit
the branch was opened to make is the one at the bottom. A body without that
signature is never touched, and neither is the diff.

Two limits are deliberate. It runs on `opened` and `reopened` only, so a
description corrected by hand afterwards stays corrected; and where the branch
offers no usable commit subject it writes nothing at all, because a title
invented from an empty branch would be worse than the generated one it
replaced.

Reopening repairs a pull request only while its body is still the platform's
original. Once this workflow has rewritten a body, the signature is gone and
it will not act again — so a pull request rewritten by a version of the
workflow you have since fixed stays as that version left it.

If v0 ever stops generating descriptions, delete the workflow and its script.

### v0 cannot amend a commit it has already pushed

Worth knowing before you rely on a fix-it-afterwards workflow. v0 pushes
branches and opens pull requests through its GitHub integration, and that
integration does not expose a force-push. The shell falls back to plain
`git`, which has no credentials:

> The amended commit is ready locally, but the force-push could not complete
> because this environment has no GitHub authentication.

Observed 2026-08-21, fixing a rejected commit trailer. v0 read the failing
check, diagnosed it correctly, amended the commit, and still could not
deliver it. The pull request was closed and the work redone from a fresh
chat rather than force-pushed from a terminal.

Two consequences:

- **Anything that must be right in a commit message has to be right when the
  commit is made.** There is no correcting it later from inside v0.
- **When v0 says it cannot push, believe it and do not retry.** It is
  describing a boundary of the platform, not a transient failure. Push the
  correction yourself, or redo the task.

## 5. A git caveat worth knowing

While fixing the above, v0's `git push --force-with-lease` was refused —
correctly, its remote-tracking ref was stale. It then proposed
`git fetch && git push --force-with-lease`, which **defeats the protection**:
fetching updates the tracking ref so the lease compares the remote against
itself and always passes. It is `--force` with the safety removed.

The correct form pins the SHA you actually verified:

```sh
git push --force-with-lease=<branch>:<expected-sha> origin <local>:<branch>
```

It also never landed the rewrite across four approval prompts, because the
sandbox loses local history between them. If a v0 rewrite loops, finish it
from a normal checkout rather than re-approving.

## 6. Branch protection

Same as every platform, and v0's model fits it better than most: it creates
its own branch and opens a PR, so a protected base branch never obstructs it.

Repository rules are free on public repositories; a private repo needs GitHub
Pro, Team, or Enterprise. This repo's ruleset is committed at
[`.github/rulesets/main.json`](../../.github/rulesets/main.json) and can be
imported. Configure it with **no bypass actors**.

## 7. Smoke test

Start a chat on the imported repo and ask *"What are your rules for making
changes in this repo, and where do they come from?"*

A correct answer names `AGENTS.md` and, ideally, `.agents/skills/`. If it
answers with generic good practice and names neither, the most likely cause
is that the import was scoped to a subdirectory rather than the repo root
(§1).

Then make a real content change phrased the way a client would phrase it, and
confirm the diff touches only `content/` — reading the **file list**, not the
PR description.
