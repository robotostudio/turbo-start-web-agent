Every page in this template lives as an `.mdx` file under `content/pages/`, and its body is just
Markdown with a handful of capitalised tags dropped in wherever a section needs more structure than a
paragraph can give it. Write `# Pricing` and get a heading. Write `<Hero title="..." subtitle="..." />`
and get the same hero section every other page on the site uses, with the same spacing, the same
responsive behaviour, and the same design tokens.

The trick is that a Block is just a React component with a name the MDX runtime recognises. `MdxContent`
compiles the page's body and hands it a components map — the full Block registry, plus a handful of
Markdown element overrides for headings, paragraphs, and lists. When the compiled MDX runs, `<Hero>`
resolves against that map exactly the way `<h1>` resolves against the browser's built-in tags. No
per-page import statement, no wiring — the Block is available because its name is in the registry,
full stop.

That registry is also the guardrail. Each Block ships with a schema, and a page that passes a Block the
wrong prop shape — a missing `title`, a `primary` link without an `href` — fails at build time, not in
a client's browser three weeks after launch. The failure is loud and specific, pointing at the file and
the prop, which matters more than it sounds like it should: content that only breaks quietly is content
nobody trusts enough to edit.

In practice, composing a page means picking Blocks the way you'd pick paragraphs. A landing page might
run `Hero`, then `FeatureGrid` to lay out what the product does, `Testimonial` for social proof, and
`CTA` to close. An about page might skip Blocks almost entirely and just be prose. Nothing forces either
choice — the same MDX file can mix both freely, which is the point. Check `/blocks-gallery` for every
Block currently in the registry, rendered live with the props it expects.
