## What this is for

Every client site ends up with the same small problem. The build goes well,
everyone signs off, and three weeks later someone needs a price changed on one
page. The usual answers are a CMS nobody maintains or a queue of one-line copy
changes sitting in a developer's inbox.

Harbour is the third answer. The client's team edits through the AI agent they
already use; your developers keep working in git; and every change lands as a
branch and a pull request, so a person still reviews what ships.

## Content is MDX in git

Pages live under `content/`. Each page is data, not code: you assemble Blocks
and pass them literal values. There is no CMS and no database.

Site chrome is not MDX. The site name, header menu, footer, and the site-wide
announcement bar are YAML under `content/settings/`, validated by the same
pipeline. Nothing under `src/` names the brand — if you find yourself editing a
company name inside a `.tsx` file, that is a bug in this template, not a step in
the process.

## Blocks, not page templates

A page is an MDX file where prose and Blocks sit side by side. Headings,
paragraphs, lists and tables render as ordinary Markdown; a Block is a
capitalised tag dropped in wherever a section needs more structure than a
paragraph can carry.

```mdx
<Hero title="…" primary={{ label: "…", href: "/…" }} />
```

No imports and no wiring — Blocks are in scope in every content file. The
registry ships fourteen today, and each one renders live with its exact props on
the [blocks gallery](/blocks-gallery). Almost every task is composing what is
already there. Adding a Block is a code change with four touch points that move
together: a Zod schema, a component, a regenerated catalog, and the registry
guard test that fails if the two halves drift apart.

## Design tokens, one file

Blocks and primitives never carry a raw hex code or a pixel value. They
reference the custom properties defined in `globals.css`, so a rebrand is a
token swap: the Block tree and the copy stay exactly where they are while the
new palette, type scale and spacing carry across every section at once. Tokens
may be given new values, never renamed or removed — every Block references them
by name.

## The build is the gate

Bad frontmatter or bad Block props fail the build by design. If the build
passes, the content is valid.

The lockdown is the part that has to be right. MDX is not a document format —
it compiles to a JavaScript module — so "the agent may only edit content"
guarantees nothing on its own. The plugin walks both the MDX tree and every
expression inside it and rejects anything that isn't a pure literal: no imports
or exports, no function calls or identifiers, no raw HTML elements, no event
handler props, and no URL that isn't a plain string on a safe scheme. That is
what turns the rule into a guarantee rather than a request.

A green build is necessary but not sufficient. Schemas enforce shape, not
meaning — they will happily ship four well-formed stats that say the wrong
thing. Read the rendered page before calling a change done.

## How a change reaches the site

An edit is proposed, not published. The agent writes to a branch and opens a
pull request; CI runs the same checks a developer runs locally — content
validation, catalog and gallery drift, lint, tests, types, and a full build that
renders every page. A human merges. Nothing reaches the live branch by any other
route.
